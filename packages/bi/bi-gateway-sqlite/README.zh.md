# @deepseek-ai/dsh-bi-gateway-sqlite

[English](README.md) | 中文

## 概述

`dsh-bi-gateway-sqlite` 在 SQLite 目录之上提供 `ctx.biGateway`。它为每个上游项目铸造稳定的 `BiProjectRef`，对着数据源对账目录，把每个项目注册为受治理资源，在每次面向成员的调用时按项目评估访问，并记录发生了什么。它只运行在 Control Plane。目录记录项目*是什么*，不记录任何人问了它什么：没有图表、行、查询或凭据的列。

<a id="use-this-package"></a>
## 使用本包

在 `team-control-plane` 组合中，把它挂载在访问控制、审计和一个 BI 数据源之后。

### 最小配置

```yaml
- name: '@deepseek-ai/dsh-bi-gateway-sqlite'
  config:
    path: /var/lib/dsh/control-plane/bi.sqlite
```

| 字段 | 默认值 | 含义 |
|---|---|---|
| `path` | — | 目录数据库所在位置 |
| `defaultChartPageSize` | `20` | 调用方未指定大小时一页列表持有的图表数 |
| `defaultMaxRows` | `200` | 调用方未指定上界时一次执行返回的最多行数 |

### 同步

一次成功的完整列表在单个事务中应用，然后与访问控制对账。新的上游 id 创建一行并注册一个已启用的受治理资源。已知的 id 更新显示名、描述以及项目的类型与仓库，而不改变引用、资源 id 或任何授权。在成功列表中缺失的 id 被退役：先删除其受治理资源，连带指名它的每条授权，然后删除该行。手动停用永远不被同步覆盖。

不应答的数据源保留上一份成功快照并记录失败。一次故障不得停用组织治理的每一个项目。并发调用者加入正在进行的对账，而不是在同一批行上竞争两次。

### 授权

每次面向成员的调用都对指名的项目重新评估 `bi.query`。未知项目、已停用项目和未授权项目产生相同的拒绝，以相同方式记录，因此一无所有的成员无法得知项目存在。目录枚举持久目录并关联到受管资源，永不枚举该类型的资源，因为目录管理资源与之共享类型。

图表列表先授权项目，从数据源读取整个列表，按调用方的关键词在名称、空间和描述上收窄，再对匹配结果分页。执行先授权图表引用中的项目，询问数据源图表在哪，当数据源的项目不一致时以 `chart-unavailable` 拒绝且什么都不执行；只有在此之后才执行图表，使用调用方的行数上限或部署的默认值。

<a id="understand-the-implementation"></a>
## 理解实现

### 两个无法一起提交的数据库

访问控制对角色、授权和资源保持权威；本目录记录项目是什么。因此对账是幂等且反复进行的：在两者中的第一个之后失败的写入，由下一次同步发现并修复，而不是留作永久的不一致。在此期间，没有受治理资源的目录行被隐藏而非展示，因为给角色编辑器提供一个任何授权都无法指名的 id，比晚一点展示一个条目更糟。

### 源码地图

| 文件 | 内容 |
|---|---|
| [`src/schema.ts`](src/schema.ts) | 两张表、其约束，以及应用 id 与 schema 版本 |
| [`src/index.ts`](src/index.ts) | 同步、授权、列表、执行与审计 |

### 一次操作记录什么

每次操作一条审计行——`bi.charts`、`bi.query` 或 `bi.catalog.sync`——携带身份、受治理项目、结果、有界的条目计数和关联 id。上游失败携带封闭的 `biFailure` 标签而非新的审计原因。图表名称、行数据和成员搜索用的关键词无处落地；畸形的图表引用不指名任何项目，也不针对任何项目记录。

## 模型体验

无，因为网关运行在 Control Plane，而 Control Plane 不挂载 agent 与工具注册表，模型永远触及不到它。

#### KV Cache 影响

这里没有请求前缀的变化。行数据只有在 Runner 侧工具渲染之后才对模型可见，其前缀成本落在那里。

## 已知限制与延后工作

<a id="known-limitations-and-deferred-work"></a>

这些限制定义了提供方何时单靠自身并不完整。它们是当前的包约束。

- **单个活动实例**——一个 SQLite 文件支持一个带持久存储与备份的活动 Control Plane 进程。水平副本需要共享数据库设计，而不是复制此文件。
- **授权逐个评估**——目录对每个项目评估一次；列表或执行对其指名的那一个项目评估一次。几十个项目的规模下没有问题；批量访问控制操作必须保留逐资源评估与策略版本语义，而不是对多个操作只授权一次。
- **关键词读取整个列表**——收窄在这里进行，作用于数据源应答的列表，因此每次图表列表都要付出一次到提供方上界的完整上游读取。
- **对账按列表全有或全无**——无法铸造引用的条目，或目录拒绝其行的条目，会回滚整个列表，因此一个畸形的上游项目会阻塞其他项目，直到数据源修好。
- **退役不可逆**——成功列表不再命名的项目连同其受治理资源和其上的每条授权一起被删除。因此只列出所持有内容子集的数据源会让管理员失去他们做出的授权。
- **这里不调度同步**——`sync` 在调用方要求时运行。启动时和周期性的对账属于知道本 Control Plane 服务哪个组织的组合，本包并不知道。
- **schema 版本会搁浅现有文件**——`SCHEMA_VERSION` 单调递增且双向拒绝，没有迁移代码。文件中的授权与管理员开关正是删除它是错误答案的原因；版本提升需要一份有文档的列修复。

#### 对账形态与知识库网关共享

来源行、串行化同步、全有或全无的列表应用、先于行的退役、资源注册和审计记录，与 `dsh-knowledge-gateway-sqlite` 承载的机制相同，只是这里针对项目目录而非知识库目录书写。克隆检测器会报告这些共享片段。抽取一个由两个网关参数化的受治理目录辅助模块是后续工作；它会触及知识库网关及其测试，这正是它没有随新增本包的变更一起进行的原因。

</details>

**运行时不变量：** 不发布伴随包：提供方不发布事件流；"返回的每一行都来自本请求已授权项目中的一张图表"在 `query` 内部强制执行，并由本包的测试断言。
