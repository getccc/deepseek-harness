# Agent Note: Team 桌面端从 Control Plane 自更新

Status: proposed

[English](2026-09-20-team-desktop-self-update.md) | 中文

## 问题

成员升级的方式是从官网下载 280 MB 的磁盘映像或 231 MB 的安装程序，覆盖安装到正在运行的应用之上。每次发版都要很久才能到达成员手里，修复了他们工作中断的构建，也只有在有人告诉他们存在时才会装上。

答案所需的三块已经在这个仓库里，彼此没有连起来。[`dsh-team-update`](../../../../packages/team/team-update) 判定一个待装版本是否可以替换此处运行的版本——Ed25519 清单签名、版本数字顺序、`minimumFrom` 升级路径、平台产物——但没有任何消费者。[`apps/desktop`](../../../../apps/desktop/src/update-coordinator.ts) 为上游个人版 Desktop 运行着一套完整的 `electron-updater` 协调器，通过 `generic` 提供方发布在公网下载源上。[`apps/team-runner-desktop`](../../../../apps/team-runner-desktop/src/main.ts) 两者都没有：它的窗口加载 `http://127.0.0.1:3090/team/open`，既无 preload 也无 IPC 通道，页面里没有任何东西能够到达外壳。

部署方式排除了那个显而易见的答案。成员在公司内网运行应用，其中 Control Plane 是已安装构建唯一已经信任的地址：[`resolveDeployment`](../../../../apps/team-runner-desktop/src/deployment.ts) 拒绝任何非 HTTPS 的打包 Control Plane 地址，因此每个部署都终结 TLS，而构建随身携带了签发它的私有证书颁发机构。官网是明文 HTTP。Windows 代码签名证书尚不存在；macOS 构建已签名并公证。

本项目发布的版本号会在这一切运行之前先让判定失效。`versionComponents` 只读三段数字并忽略 `-` 之后的一切，因此 `0.1.6-alpha.1.20260917.2` 与 `0.1.6-alpha.1.20260918.1` 都是 `0.1.6`，比较结果相等，`decideUpdate` 回答 `not-newer`。

## 提案

通过已安装构建已经信任的 Control Plane 发布每个版本，用 `dsh-team-update` 作判定，用 `electron-updater` 下载与安装，并把这个控件放在侧边栏底部成员条目旁边。

### 发布版本是三段递增的数字

发布构建采用 `x.y.z`，每次发版递增。连字符之后可以跟构建戳供支持排查使用，但决定是否升级的只有这三段数字，因为 `compareVersions` 只读这些。官网写死的 `v2.3.0` 与打包版本号合为同一个字符串，从发布的清单读取，而不是写两遍。

### Control Plane 提供版本

nginx 把 `/updates/` 作为静态目录服务在控制台旁边：签名清单、`electron-updater` 元数据、各个产物以及各自的 `.blockmap`。静态文件会响应 `Range` 请求，而差分下载需要它；若在其前面放置应用层代理，该代理必须自行回答 `206`。

清单请求携带成员的设备身份，因此由 Control Plane 按设备决定一份清单提供哪个版本。分批放量与强制最低版本就是这个判定，而不是第二套机制。产物请求不鉴权：280 MB 的下载会超出账号令牌 60 秒的刷新提前量，而让这些字节可信的是签名。

### 清单签名顶替缺失的 Windows 证书

发布私钥留在发布机上并在那里签署清单。Control Plane 只存储和分发收到的内容，不持有任何密钥。客户端用随包携带的公钥验证签名，从已验证的文档中读取产物摘要，`electron-updater` 会拒绝哈希不符的下载——差分下载也在其中，因为组装后的文件在安装前会被哈希。

被劫持的内网连接可以扣住一次更新，或者提供一份更旧的已签名清单，而后者被 `not-newer` 拒绝。它无法让客户端安装发布密钥未曾背书的字节，而这正是 Windows Authenticode 证书本来要提供的性质。等那张证书到位，`publisherName` 会在这层之上再加操作系统自己的检查。

### 外壳自带一个与 Desktop 同构的协调器

Team 外壳自带协调器，构造方式与 `apps/desktop` 中的那个相同：相同的检查与安装阶段、同一时刻只有一个在途操作，以及状态出口、更新器与启用条件这几个相同的构造参数。它不是共享代码。`@deepseek-ai/dsh-desktop` 是没有导出面的私有应用，而 `pnpm run duplication` 读取的是 `packages` 与 `scripts` 而非 `apps`，因此为一个类提取共享包在今天要付出新增一个包分组的代价；提取留作后续项，两个协调器保持结构一致以使其代价始终很低。它的 `beforeRestart` 钩子正是 Team 外壳停止 Runner 并等待端口与可执行文件被释放的位置，Windows 要求安装程序替换文件之前先完成这一步。

`electron-updater` 通过 Electron 的网络栈发请求，该栈读取操作系统信任库，因而会拒绝本部署的私有证书颁发机构。外壳用 `session.setCertificateVerifyProc` 仅为 Control Plane 主机固定该机构，比对随包暂存的 `runner/control-plane-ca.crt`。`app.on('certificate-error')` 在此不适用：它观察的是 `webContents` 导航，而非 `net` 请求。

### 控件经由 preload 桥加入成员行

侧边栏底部的成员条目声明了一个 `team.account.action` 列表，控件就加入在那里，紧挨着成员名字。外壳通过上下文隔离的 preload 桥暴露检查、安装与状态订阅，`apps/desktop` 已经为它自己的页面这样做；外壳还在该订阅上报告下载百分比，因为 280 MB 的传输需要的不只是一个看起来很忙的按钮。一个 Team 包读取该桥并注册控件。它自己声明这座桥，而不是导入外壳的声明，因为两个程序各自独立编译；`protocolVersion` 正是二者漂移时的绊线。在 3090 端口打开的浏览器和源码启动都没有这座桥，该包不注册任何内容，也就不渲染控件。

### 打包产出更新程序所读的内容

macOS 构建新增 `zip` 目标：Squirrel.Mac 从 zip 替换应用，磁盘映像仍作为手动下载渠道。zip 在公证与 staple 之后产出，因此落地的正是已公证的包。两个平台都已经产出 `.blockmap`。发布步骤签署清单，并把产物、清单与 blockmap 一并上传。

插件树的代次标记从应用版本改为该树的内容指纹，因为目前一次携带相同插件的升级仍会在 Windows 首次启动时重新复制 959 MB。

### 控制台发布一个版本

管理控制台新增发版页面：登记一个版本及其签名清单、选择向谁提供、设置低于则应用拒绝运行的最低版本、撤回某个版本，以及读取现有设备记录中已有的版本分布。产物通过 `scp` 送达主机：nginx 的请求体上限是 40 MB，让 280 MB 通过控制台上传需要另一套机制，且没有收益。

## 考虑过的替代方案

**从官网提供更新。** 官网与公网 Control Plane 同处一台主机，因此在那里放一个静态 `/updates/` 是可行的，且不需要新路由。否决的原因是官网为明文 HTTP，更关键的是更新地址必须跟随构建打包时所指向的 Control Plane——内网部署与公网部署是不同的服务器，第二个地址将不得不同样被打包、校验，并与第一个保持同步。

**让上游客户端包直接读取该桥。** 控件也可以改为加入 `sidebar.footer.action`——`ui-sidebar` 已经声明、尚无占位方的列表，那会把它放在成员条目上方一行，而不是紧挨着成员。两点都不成立：这个控件该在的正是成员自己那一行，而从上游浏览器包读取外壳拥有的全局对象，会让桌面外壳成为每个部署 Web 界面的隐性依赖。真正读取它的那个 Team 包，只在外壳能够据其报告采取行动的地方分发。

**经由 Runner 到达外壳。** 在派生的 Runner 上加一条 `ipc` 通道再加一个 BFF 控制器，可以让更新状态走既有请求路径，与 `open-in-app` 和 office 选择器的构建方式一致。否决的理由是它是两个正确答案中更大的那个：它为搬运 preload 桥本就携带的状态添加了一套进程协议和一个 API 包，而且 Runner 独立于外壳重启，那条通道还需要自己的重连规则。

**自行编写下载与安装。** 在 macOS 上替换正在运行的 `.app` 意味着驱动 Squirrel.Mac 或重新实现它，而 Windows 的安装程序替换必须在自身可执行文件被覆盖的情况下存活。`electron-updater` 两件都做，且已经是本仓库的依赖，其差分下载的实测见下。

**只分发变化的部件。** `dsh` 可执行文件占了整包 278 MB，插件树占了余下的大部分，因此只替换其中之一能少搬运很多数据。因 macOS 而否决：交付在应用包之外、从成员数据目录运行的可执行文件不在该包的公证覆盖范围内，而 Gatekeeper 对这类文件的处置不是可以拿来搭建发布路径的东西。

**等待 Windows 证书。** 否决的理由是签名清单已经为这些字节提供了该证书本要提供的性质，而证书剩下的好处——操作系统对发布者自己的判断——并不构成该机制的前置条件。

## 验收标准

一个被提供了更新的已签名版本的 macOS 打包构建，会在侧边栏底部显示该控件，点击后下载，并重启进入新版本，成员的会话、设置与凭据保持完好。

Windows 打包构建行为相同，且其安装程序在先前的 Runner 已退出的情况下替换文件，通过在应用已处于运行状态的机器上执行一次升级来验证。

签名、版本或平台产物未能满足 `decideUpdate` 的清单不会产生任何下载，拒绝原因会写入外壳日志。

低于清单 `minimumFrom` 的构建拒绝该更新，而不是跨越不受支持的间隔安装；比已安装版本更旧的清单被以 `not-newer` 拒绝。

Control Plane 对产物响应 `Range` 请求，且一次差分下载无需取回整个文件即可完成。

在没有外壳的情况下——3090 端口的浏览器，或源码启动——侧边栏不渲染更新控件，该包不注册任何内容。

聚焦测试覆盖判定路径、协调器的各个阶段、证书固定判据以及插件树指纹。客户端包自带词典，侧边栏注册由客户端测试层覆盖。

## 风险

**终端防护可能拒绝未签名的静默安装程序。** Windows 安装程序不带 Authenticode 签名，内网终端管控代理可能拦截或告警，尽管 `electron-updater` 从不把该文件标记为从网络下载。源码检查无法判定这一点；在宣布 Windows 放量之前必须在一台受管办公机上实测。

**macOS 签名身份变更会切断更新路径。** Squirrel.Mac 只会用同一身份签名的应用替换现有应用，因此被替换而非续期的身份会让每个已安装构建只能手动重装。

**这台主机自己承担下载。** 两个平台各保留三个版本约占 1.5 GB，而一次发版会从每位成员处引来 150–280 MB 的下载。公网主机的磁盘已接近饱和运行；内网主机尚有余量。`/updates/` 需要自己的限速，客户端的检查需要抖动。

**差分下载的收益并不均匀。** 由两次连续的真实构建的 blockmap 实测：一次只改了一个浏览器包的 Windows 发版，220.8 MB 的包只需取 22.0 MB；而跨一天工作量的 macOS 发版，280.4 MB 中需要取 155.3 MB，因为重新签名与重建的可执行文件移动了大部分块。macOS 成员应当预期这个量级的下载。

**首次安装仍不受保护。** 官网是 HTTP，因此初次下载可能在传输中被替换，浏览器对以这种方式提供的可执行文件本就会告警。自动更新是端到端签名的；在官网启用 TLS 之前，第一次不是。
