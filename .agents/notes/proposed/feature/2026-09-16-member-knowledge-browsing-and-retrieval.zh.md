# Agent Note: 成员在会话之外阅读和检索私有知识

Status: proposed

[English](2026-09-16-member-knowledge-browsing-and-retrieval.md) | 中文

## 问题

私有知识目前只以"模型代成员完成的动作"这一种形式到达成员面前。[第一阶段](2026-09-01-team-private-knowledge-control-plane.zh.md)交付了已授权目录和段落检索，两者都在会话内部被消费：`/knowledge` 选择范围，提示词声明该范围，`knowledge_search` 取回的段落只作为回答里的一条工具结果被成员看到。

由此有三件成员需要的事无法做到。他们看不到知识库里有什么——目录只列出知识库本身，因此正在判断是否选中某个知识库的成员只能靠猜。他们无法阅读文档：检索返回的是段落，段落所属的文档被命名了却打不开。他们也无法评判检索本身——一个查询是否找到了正确的材料，排名如何排序——因为每次检索都埋在模型轮次里，模型会改写结果，且从不展示得分。

第一阶段把文档全文阅读列为明确推迟的第二阶段。文档列表则不是被推迟，而是根本没有设计过，因为面向模型的检索能力不需要它。现在两者都是产品必需，而且必需发生在会话之外——想查一份资料的成员不应该被迫先开一个会话。

## 提案

以左侧导航进入的两个全局面板交付面向成员的知识能力，并为此扩展知识 seam 的两个操作：列出已授权知识库中的文档，读取一份文档的内容。

### 产品结果

- 成员在 Team 构建的左侧导航中，于**新工作任务**下方看到**知识库**和**知识库检索**。不含私有知识的构建两者都不显示。
- **知识库**打开的面板以卡片展示成员角色已授权的知识库，每张卡片给出它有多少份文档，以及知识源创建它的日期。打开其一，在一条可回到上一层的面包屑下列出其文档；打开一份文档，则在面板右侧的抽屉中绘制它。
- **知识库检索**打开的面板执行一次检索，按得分排名展示段落，并按各自所属文档分组，不启动模型轮次，也不消耗 token。
- 选中某条结果的文档会新建一个会话，其知识范围收窄到这一份文档，因此随后的对话只从它检索，不从别处检索。
- 面板的每个操作都在 Control Plane 上按当前授权审批，与 `knowledge_search` 现在的做法完全一致。撤销角色、停用成员、吊销设备或停用知识库会改变下一次面板操作，无需重新登录。

### 本阶段的非目标

- 不提供上传、删除、重新解析、文件夹编辑、打标签或任何其他对上游知识的修改。两个面板都是只读的。
- 不在成员电脑上持久化文档、段落或目录。预览字节是临时的 UI 输入，不进入任何工作区、缓存或附件存储。
- 不向浏览器返回上游 URL、上游标识符或凭据。面板只通过 DSH 引用寻址知识。
- 不新增面向模型的文档阅读工具。模型的检索能力仍然只有 `knowledge_search`；本阶段收窄该工具可触及的范围，不增加它可调用的东西。
- 不暴露 WeKnora 的成稿回答、自定义 agent 或会话续接。

## 成员从左侧导航进入什么

左侧导航已经有现成的位置：`sidebar.panellist` 是一个列表槽，其行直接渲染在新对话和新工作任务条目下方，每行按同一个 id 指向一个 `main` 面板（[contract/slots.ts](../../../../packages/client/ui-sidebar/src/client/contract/slots.ts)）。目前还没有任何生产插件注册到它；这两行是第一批，侧边栏外壳无需改动即可承载它们。

两个面板都是 root 作用域，不持有会话。因此知识库面板自己绘制文档，而不是打开右侧 Sidebar——后者的标签页按会话划分，其停靠面也按会话创建。

在面板内部，采用的是两个层级加一个抽屉，而不是并排分栏：先是卡片，再是某个知识库的文档与一条回到上一层的面包屑，最后是面板右侧覆盖的一份文档。分栏会把每一层都固定在三分之一的宽度上，无论成员此刻是否在读文档；而无论如何，成员在列表上方需要的就是这个知识库的名字。

卡片上的文档数量与创建日期取自治理目录的镜像表，而不是一次实时的上游读取：目录是一个授权答案，让它去触及知识源，等于把知识源的可用性摆在一个只想看看有什么的成员面前。数量原本就已镜像；创建时间的代价是目录表多出一个可空列 `knowledge_base.upstream_created_at`，以及 `SCHEMA_VERSION` 升到 4。这个版本号就是全部代价，并且在持有旧文件的部署上需要手工支付，因为本仓库不为自己的 SQLite 存储提供迁移代码。

这也把面板与右侧 Sidebar 已注册的文档正文渲染器隔开，而这是这个形态唯一的代价：渲染器槽由 Sidebar 自己的标签页类型声明并按会话划分，因此 Word、Excel 和 PowerPoint 的正文无法从一个没有会话的面板中渲染。于是抽屉绘制浏览器仅凭字节就能绘制的东西——PDF、图片、任何属于文本的内容——外加 Control Plane 回落到的解析文本，并明确说明 Office 文件在这里还显示不了。要弥合这个缺口，需要一个两个界面都能触及的渲染器座位，而那是对 Sidebar 契约的另一次改动。

## 知识文档引用

文档引用由其知识库引用、一个 `/` 和上游文档 id 组成：`weknora:lingang:<kbId>/<docId>`。它是与 `KnowledgeRef` 不同的品牌，有自己的校验和自己的长度上限，因为 `KnowledgeRef` 被审计存储的 `resource_id` token 限制在 64 个字符，两个上游 UUID 放不进去。这样分开不损失任何东西：审计行记录的是知识库资源，那才是授权所命名、管理员所停用的对象。

每个接受文档引用的操作都会在上游解析该文档，并在其所属知识库不是引用中所命名的那个时拒绝。这项校验正是不签名的引用仍然安全的原因：持有引用本身不证明任何事，引用中的知识库在每次调用时被重新授权判定，两半互相矛盾的引用在读取任何内容之前就被拒绝。它替代了第一阶段勾勒的"带有效期窗口的签名引用"，后者需要签名密钥、轮换手册，以及两个对某些会话必然取错的边界值。

## Control Plane API 新增

| 方法与路径 | 操作 | 行为 |
|---|---|---|
| `POST /team/knowledge/documents` | 文档列表 | 校验设备 Token，对具名知识库做授权判定，列出其文档的一页，返回文档引用、标题、文件类型、大小和解析状态 |
| `POST /team/knowledge/document` | 文档内容 | 校验设备 Token，解析出文档所属知识库并做授权判定，返回原始文件字节及其内容类型和文件名，字节不可用时返回解析后的文本 |

两条路由都携带 `protocolVersion`，并在请求所声明的版本不被本次构建提供时于解码任何其他字段之前被拒绝，与现有两条完全一致。新增路由会上调当前知识协议版本，最低版本保持不变。版本属于请求，而不属于 Runner：本阶段之前构建的 Runner 仍能检索、仍有目录，只是没有面板去调用新路由；而比自己所连 Control Plane 更新的 Runner 同样保有这两项操作，只在它请求该部署从未有过的路由时被拒绝。

请求体依然不命名组织、主体、设备、源站、租户、凭据或上游标识符。文档引用是唯一的新字段，而它是一个由网关自行解析的 DSH 引用。

## 本阶段使用的上游操作

与第一阶段的合约 fixture 一样，对着部署自身的路由和处理函数固定：

| 用途 | 端点 | 上游访问级别 |
|---|---|---|
| 知识库中文档的一页 | `GET /api/v1/knowledge-bases/{id}/knowledge` | viewer，知识库读 |
| 一份文档的元数据，包含其知识库 | `GET /api/v1/knowledge/{id}` | viewer |
| 原始文件字节，按文件名定类型以便浏览器内展示 | `GET /api/v1/knowledge/{id}/preview` | viewer，知识库读 |
| 一份文档解析后的分块文本 | `GET /api/v1/chunks/{knowledgeId}` | viewer |
| 收窄到具名文档的检索 | 现有 `hybrid-search` 请求体中的 `knowledge_ids` | 不变 |

`GET /api/v1/knowledge/{id}/download` 提供同样的字节，但在上游要求 contributor 权限和知识库写访问，因此本阶段改用 `preview`。这个区分与部署持有哪种凭据无关——它是说，只读的产品能力不应建立在一个上游守卫为写守卫的端点之上。

检索命中本来就携带 `knowledge_id` 和 `knowledge_title`，而提供方目前丢弃了前者。保留它正是排名结果能够命名其文档的前提，也是现有检索路径唯一需要的改动。

## 文档级会话范围

恰好命名一个知识库的 `selected` 范围，通过该记录条目上的可选 `documents` 携带其中的文档——每一项是一个引用加上它被选中时的标题。

它是一个可选属性而不是独立的 mode，原因在持久化机制而不在口味。新增联合成员被归类为「类型发生变化」，这要求升 `SESSION_FORMAT_VERSION`，并带上整套相邻迁移装置：一个格式包、一条带逐工件阶段的身份边、快照后继、历史格式文档，以及一个 `release/*` 集成基。而新增可选属性属于 same-version。这个特性不值得占用一个格式代际，因此采用规则允许的形态（[记录](../../../../docs/persistence-changes/2026-09-16-knowledge-scope-documents.zh.md)）。

这个选择有一个代价，而且是写明而非藏起来的：早于该字段的构建会忽略它并检索整个知识库——比成员所选更宽，绝不会更窄。要触及它，需要成员在较新构建上记录了收窄范围、把打包的 Runner 降级，然后恢复该会话。换成新增 mode 则会让旧构建直接拒绝该日志，这更干净，代价是一个格式代际。

每份文档的标题都记录在它的引用旁边，提示词据此点出这份文档。关于一份报告的对话应当能说出是哪份报告，而模型可见的名字必须来自日志。标题是成员看到的那个，由浏览器发来，controller 把它折叠为一行、至多 200 个字符：没有描述单份文档的受治理操作，而且标题是一个标签，不是授权事实——被授权的是装着这份文档的知识库。该字段尚未发布，因此它在同一份确认记录里替换了只含引用的 `docRefs`，而不是再叠加一份；记录过 `docRefs` 的开发日志会被读作整个知识库，与旧构建承受的降级相同。

## 文档对话是一个能检索的聊天

打开关于某份文档的对话会创建一个聊天会话：读一份报告的成员不应先去挑一个工作目录。内置的 `chat` preset 用 `allow: []` 遮蔽所有宿主工具，在本次改动之前这也包括 `knowledge_search`，于是这样的对话记录了一个范围，模型被告知了它却用不上。`dsh-tool-restriction` 现在接受 `allowWhenRegistered`，chat preset 把 `knowledge_search` 列在其中。它只在 Team 部署注册了它的地方可见，而工具自己的规则仍然在记录知识范围之前把它藏起来，因此普通聊天不发送任何工具 schema。

另一个方案是一个持有同样组合的 Team 专属 preset。它的根目录必须是已安装 bundle 内部的绝对路径，要在打包的 Runner 里于加载时解析；而 chat preset 本来就以完全相同的方式携带一个按会话开关的工具。所选方案的代价落在遮蔽行上：`allowWhenRegistered` 里的名字没有拼写检查，并且列表只在挂载时读取一次。

文档以附件文件的样子显示在 composer 上方，由 `ui-knowledge` 的文档坞为每份文档显示一个 chip，其 × 会移除它；最后一份被移除时知识被关闭，而不是扩大到成员从未选择过的知识库。

有两条不变量落在校验器里而不是约定里：每个文档引用都必须解析到携带它的那个知识库；命名多个知识库的范围根本不能携带文档，因为上游的收窄只在一个知识库内生效。

## 文档预览的传输与上限

Control Plane 在配置的 `maxDocumentBytes` 之内返回完整文件字节，Runner 则以工作区文件已有的完整字节传输方式交给浏览器：一份 base64 载荷经现有远程方法传输，解码成渲染器读取的 `DocumentContent`。Runner 上不新开任何通道。

两个上限是有意分开的。源提供方上的 `maxDocumentBytes` 是 Control Plane 愿意从上游拉取并驻留内存的量；控制器自己的上限是浏览器愿意解码的量。超过任一上限的文档不是需要成员自己解决的错误：面板回落到解析后的分块文本，这同样服务于没有任何已注册渲染器认领其类型的文档。

## 权限

本阶段由 `knowledge.search` 准许文档列表和文档阅读。权限目录中的 `knowledge.read` 和 `knowledge.download` 保持第一阶段留下的未授予状态。

这是对该阶段的一处有意偏离——它曾把文档全文阅读列为独立的授权——需要记录的理由是：这个偏离是产品决策而非疏漏，能从某个知识库检索段落的成员，也可以打开这些段落所在的文档。有两件事让它保持可逆。网关按每个操作从一个常量读取自己判定的动作，因此把文档阅读收紧到 `knowledge.read` 就是改这个常量加上角色编辑器里的一档，而不是重做一层授权路径。文档阅读还以自己的动作记入审计，因此即便一条授权同时准许两者，审计仍能把"检索了段落"和"打开了文件"分开。

## 审计

`knowledge.document.list` 与 `knowledge.document.read` 以现有知识动作所用的封闭元数据加入 `AUDIT_ACTIONS`——一个有界计数和上游失败标签。两者都记录知识库资源、从不记录文档，因为文档不是受治理资源，而文档标题是散文。

对已存在的存储而言新增动作是安全的：动作和元数据键在每次打开时以插入方式重新播种。审计原因不是，这也是上游失败种类继续以标签而非新的 `AuditReason` 到达的原因。

查询、标题、文件名、段落、字节和上游错误仍然不进入审计存储和普通日志。

## 交付计划

四个变更，每个都可独立上线。

**检索面板与两个导航行。** 新客户端包、两个导航行、知识库检索面板，以及控制器的 `search` 和 `directory` 远程方法。不改 Control Plane 路由，不加新权限：它跑在已经上线的检索路径上。选中结果会以该结果所属知识库为范围新建会话并引用命中段落，这一行为由最后一个变更替换。

**文档列表。** 贯穿五层的 `documents` 操作、列表路由、其审计动作，以及知识库面板的文档列表。

**文档内容。** `documentContent` 操作、内容路由、抽屉，以及分块文本回落。

**文档级范围。** 被记录的 `documents`、读取它的提示词段落与检索请求、显示它的选择器与输入框 chip，以及检索面板中收窄到文档的会话。

## 备选方案

**在右侧 Sidebar 中预览。** 右侧 Sidebar 今天拥有文档预览能力，包括 Office 渲染器，复用它可以白得分屏、浮窗和多标签页。但它的标签页按会话划分，其停靠面按会话创建，而这两个面板是 root 作用域、有意不持有会话；给面板配一个会话，等于凭空造一个只为装下预览而存在的会话。改由面板自己绘制文档，代价是 Office 正文留在那道会话边界的另一侧。

**只预览解析后的分块文本。** 最省也最安全：没有公司文件离开 Control Plane，命中段落还能就地高亮。代价是丢掉了文档本身——版式、表格、图片和分页结构，恰恰是打开一份报告的成员要看的东西。分块文本作为回落保留，服务于超出字节上限或没有渲染器认领其类型的文档。

**为浏览与阅读设立第二条授权。** `knowledge.read` 正是为此存在于权限目录中，第一阶段也是有意预留的。要求它意味着每个部署都要先配置第二条授权，面板才能做任何事，而产品的立场是：对某个知识库的检索权限已经蕴含阅读其文档。因此记为一处带上述两重对冲的偏离，而不是设计本意。

**带有效期窗口的签名文档引用。** 这是第一阶段为文档全文阅读勾勒的方案。每次调用都在上游校验文档所属知识库能给出同样的保证——引用无法触及调用方未获授权的知识库——而且不需要签名密钥、密钥轮换，也不需要一个对长会话或共享链接必然取错的有效期窗口。

**以知识库为范围讨论某条结果。** 以结果所属知识库开始会话并引用命中段落完全不需要改动范围类型，这也是第一阶段的现状。但它回答的不是成员提出的问题：成员选的是一份文档，而一个从整个知识库检索的会话会拿他们没有选的文档来作答。它作为第一个变更的行为保留，由第四个变更替换。

**把知识文档落到工作区。** 把文件下载进会话工作区，可以让现有文件预览直接生效，完全不需要新的内容通道。但它会把公司文档写到成员电脑上，那里没有任何机制能撤回它们，而且它把一次由 Control Plane 逐次审批的读取，变成一份比授权活得更久的文件。

## 验收标准

- 两个导航行在 Team 构建中出现在新工作任务下方，使用成员的语言，并在不挂载知识服务的构建中不存在。
- 知识库面板恰好列出成员角色已授权的知识库，列出选中知识库的文档，并以原始字节预览选中的文档；超出字节上限或无渲染器认领其类型的文档以解析文本预览。
- 知识库检索面板按得分排序返回段落及其文档标题，不启动模型轮次，不追加会话事件。
- 选中某条结果会打开一个聊天会话，其折叠后的范围就是这一份带标题的文档，提示词段落说出它，composer 以附件文件的样子显示它，并且会话会被提供只从它检索的 `knowledge_search`。
- 成员在其知识库上没有授权的文档引用会被拒绝，且该知识库未授权、已停用或不存在时拒绝方式完全相同。
- 命名了文档并不属于的知识库的文档引用，在读取任何内容之前被拒绝。
- 撤销授权、停用知识库或吊销设备会改变下一次面板操作，无需重新登录或新建会话。
- 审计存储为每次操作记录一行 `knowledge.document.list` 或 `knowledge.document.read`，记在知识库资源上，不携带查询、标题、文件名或上游文本。
- 本阶段之前构建的 Runner 面对提供新路由的 Control Plane，仍保有其目录与检索。
- 比自己所连 Control Plane 更新的 Runner，仍保有目录与面向整个知识库的检索，只在文档相关操作与收窄到文档的检索上收到 `update-required`。因此协议版本随请求传递，而不是随 Runner 传递。
- 收窄到文档的会话的提示词段落和工具可见性，在能覆盖的地方被覆盖：由各自包的测试覆盖，因为没有任何录制会话层级能触及知识库（见下面的覆盖缺口）。

## 已命名的覆盖缺口：没有录制会话层级能触及知识库

每个知识操作都经由 Control Plane，而录制会话工具只录制模型流量。因此没有任何无密钥场景能演练提示词段落、工具可见性，或一次知识检索的转录，这也是这几个阶段都没有改动 `snapshots/session/`、`snapshots/sdk/` 或 Python SDK 投影的原因：那里没有需要改的东西。

浏览器这条链路拿到的是一层装配级覆盖。`apps/web/tests/knowledge-panels.e2e.ts` 以同进程内的 fixture `ctx.knowledge` 启动出厂的插件行，在真实浏览器里操作两个面板，并回读讨论所记录的 `knowledge/scope` 事件。它也是唯一跑生成的 Remote 客户端的层级，而该客户端按声明的参数个数而非必需参数个数校验：面板调用一旦省略末尾的可选参数，在到达传输层之前就被拒绝，任何单元测试都看不到这一点。

弥合它意味着让该工具学会回放一段录制的知识传输——为面向 Runner 的路由准备一份 fixture，对真实 Control Plane 录制一次，然后像模型流量那样无密钥回放。那是它自己的一次改动；在它落地之前，这里模型可见的接口面由包级测试外加维护者手动运行的真实部署 e2e 钉住。

## 风险

**知识拒绝从未有过这么大的呈现面。** 操作从两个变成四个，每个都带同一套封闭原因，而且到达的是面板而不是工具结果。把拒绝渲染成空列表的面板，会告诉成员他们什么都访问不到，这正是第一阶段为目录指出过的失败方式；每个面板状态都区分被拒绝、为空和不可达。

**公司文档进入浏览器。** 预览把原始文件放进成员的浏览器，而那里操作系统自身的能力——打印、保存渲染后的页面、截屏——都在 Control Plane 能撤回的范围之外。本阶段限定交出的量并且不做任何持久化，同时明确这是一项读取授权控制，不是拷贝控制。

**上游分页与解析状态。** 文档很多的知识库，或上游仍在解析中的文档，会让列表成为一个移动目标。面板采用分页、展示解析状态并按需刷新，而不是缓存一份 Control Plane 还得负责失效的目录。

**那一份凭据的暴露面变宽。** 经由 Control Plane 的空间 Key 可达的上游端点多了三个。三个在上游都是读级别，提供方也仍然只调用固定集合、不接受调用方提供的路径，但 Control Plane 一旦被攻破，影响范围会从检索扩大到整份文档。

**范围变更的波及面。** 第四个变更触及一个持久化事件载荷、提示词、工具可见性、选择器和 chip。它排在最后正是因为这一点，而它之前的每一项都可以不带它上线。

**降级会放宽一个已收窄的对话。** 可选属性形态换来了 same-version 持久化，代价就是上面点明的那一条：旧构建恢复一个已收窄的会话时会检索整个知识库。无法接受这一点的部署只有一个选择——为独立的 mode 花掉一个格式代际。
