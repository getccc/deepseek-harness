# Agent Note：控制台导航是组织的数据，菜单权限就是授权

Status: implemented

[English](2026-08-31-navigation-is-data-and-menu-access-is-a-grant.md) | 中文

## 问题

[浏览器应用那篇 Agent Note](../architecture/2026-08-30-administration-console-as-a-browser-application.zh.md) 所描述的管理控制台带着一个固定侧边栏：六个视图列在 `App.tsx` 里，每个视图旁边写着一项守护它的权限。由此产生了三件事，而三件都是缺陷，不是精简。

管理员看不到组织架构，因为组织架构并不存在——账户不带部门，组织与账户之间什么都没有。于是用户表无法回答"谁在技术部"，而组织页面是一张只有一个可编辑字段的卡片，那算不上一个页面。

管理员无法在不阅读权限字符串的情况下看清一个角色允许什么。角色有一个显示名和一串 `resourceType|action`。没有任何东西把这些配对与管理员日常导航的页面联系起来，因此组合一个角色就意味着把目录背下来。

管理员无法改变控制台提供什么。调整页面顺序、隐藏部署用不到的页面、把设备与模型归到同一个标题下，全都是改源码再重新构建。

## 决定

**导航成为持久化数据，并拥有自己的 Seam。** [`dsh-team-console-menu`](../../../../packages/team/team-console-menu/README.zh.md) 声明这条记录，[`dsh-team-console-menu-sqlite`](../../../../packages/team/team-console-menu-sqlite/README.zh.md) 负责存储。一条菜单指明它的措辞、地址、渲染它的页面组件、图标、顺序、是否在服务，以及是否绘制。本构建随附的树是一个代码常量，在启动时按组织播种，并以稳定的 key 匹配：部署做过的重命名、重排与隐藏能挺过每一次重启，被删除的随附菜单则以随附设置回来。

**一条菜单声明封闭目录中的一项权限，而菜单权限授予的正是它。** `POST /roles/:id/menus` 接收角色应当可达的菜单，并让该角色的类型授权与之一致：加上每条被选中菜单所声明的权限，撤销未被选中菜单的权限，并且不动任何没有菜单声明过的配对。因此"菜单权限"是授权之上的一个视图，而不是第二套鉴权系统；管理员按页面组合角色，组合出来的仍然是 `PERMISSION_CATALOG` 里那些一直被授权命名的项。导航依然不执行任何事：每条路由都会再次询问访问控制，因此一条对一无所有的人可见的菜单只是导航配置的失误，而不是一条入口。

**组织架构存放在账户存储中。** `department` 表保存按组织划分的树，其编码在组织内唯一，另有类别、作为账户的负责人、联系方式、排序与状态。账户新增 `phone`、`gender` 与 `department_id`。两者都是账户存储的本职——一个组织以及其中的人——把部门放在这里，正是 `account_user.department_id` 能成为真正外键、而不是另一个数据库中一个 id 的原因。

**角色新增编码与创建时间。** 编码是部署自身配置用来指称角色的稳定标识，因此为读者重命名角色不会破坏任何东西。更早构建存下的角色以自己的 id 作为初始编码，它按构造即唯一；它不带创建时间，因为编造的时间戳读起来与真实的一模一样。

**控制台的四个管理页面采用请求所指定的参考形态。** 部门管理是一张树表，根行就是组织本身——编辑这一行就是过去组织页面里的那次重命名，独立的组织页面因此取消。用户管理是部门树与带筛选、分页的表格并排。角色管理承载编码、数据范围、持有者与菜单权限。菜单管理就是那棵树本身，可就地编辑。

## 曾考虑的替代方案

**把导航留在源码里，只做一个可以排序的菜单页面。** 已否决，因为请求要的是一个管理页面，而一个没有"新增"按钮的页面不算管理页面。把树存起来同时消除了侧边栏对重新构建的依赖，而那正是随附列表存在的原因。

**允许菜单命名任意权限字符串。** 出于授权不能这么做的同一理由否决：封闭目录正是让拼写错误在它被写下的地方失败的机制。后端会拒绝命名目录不治理的配对的菜单，控制台的这个字段是目录上的下拉选择，而不是文本框。

**给角色一个自己存储的数据权限设置。** 已否决，因为没有任何东西会执行它。数据范围这一列读的是授权本身——对资源类型的授权允许该类型的全部资源，对单个资源的授权只允许那一个——因此这一列不可能与角色的实际行为相矛盾。

**像参考实现那样给角色一个状态开关。** 已否决，因为"停用的角色"不是本构建拥有的概念，而一个改变了无人读取的列的控件比没有这个控件更糟。解绑角色或删除角色才是真实存在的动作。

**提供删除账户。** 在此处已否决，因为账户是审计记录与设备凭据的锚点，而停用已经让成员持有的每个会话立即失效且可逆。[后一篇 Agent Note](../architecture/2026-08-31-a-role-that-covers-the-permission-catalog.zh.md) 把这件事推进了一步：审计行确实保留，账户行则被删除。

**把部门放进菜单旁边的新包里。** 已否决，因为一个组织以及其中的账户本就是账户存储的主题，而放在另一个数据库里的部门会让账户的部门成为一个无法约束的引用。

**在 Store 内部播种导航。** 已否决，因为 Store 并不知道 Control Plane 服务于哪个组织。管理 API 是唯一在配置中命名了它的组件，因此播种是由该组件发起的调用。

## 结果

管理员可以搭建组织架构、把账户放进去、按部门筛选用户目录、按可打开的页面组合角色，并改变控制台提供什么——全都无需重新构建，且全都经由与其他所有管理写入相同的 Session、Origin、CSRF、访问控制与审计路径。

账户存储（部门与三个账户列）与访问控制（角色的编码与创建时间）的 `SCHEMA_VERSION` 各自推进。两者都是向更早构建写出的表增加列，因此两者都带上了 `CREATE TABLE IF NOT EXISTS` 做不到的增量 `ALTER TABLE`：更早构建写出的数据库会保留它的行并获得这些列。修改或删除既有列的变更仍然没有路径。

Control Plane 组合增加一行，权限目录增加 `department.read`、`department.manage`、`menu.manage`、`member.update`、`role.update` 与 `role.delete`。以命名权限的方式绑定角色的部署，必须加上这些新项，相应页面才会出现。

以下能力被推迟，并且是刻意缺席而不是做成毫无作用的控件：账户批量导入、把部门或菜单移动到另一个上级之下、删除账户、角色状态，以及按查看者保存的列偏好。控制台目前仍然面向单实例、单组织的部署。
