# Agent Note: Control Plane 管理其网关所强制执行的对象

Status: implemented

[English](2026-08-30-control-plane-administration-console.md) | 中文

## 问题

Team Edition 已经存储账户、角色、授权、设备和公司模型，但如果管理员必须调用服务方法或检查 SQLite 才能改变这些记录，它们还不是可用的产品。最初的 Team Shell 页面只在无样式表格中暴露成员、角色名称和设备。组织身份、角色内部的权限、成员绑定和模型目录仍不可见，这会让已部署的 RBAC 系统看起来像不存在，并鼓励绕过产品所要证明的同一授权与审计路径进行带外编辑。

## 决策

这里决定的呈现方式已被[浏览器应用那篇笔记](../architecture/2026-08-30-administration-console-as-a-browser-application.zh.md)取代：管理现在是一个建立在 JSON API 之上的 React 与 Ant Design 应用，而 `dsh-team-shell` 只剩设备确认页。下文所述的受治理资源、每条路由所询问的权限，以及目录的各项拒绝，浏览器应用全部保留。

`dsh-team-shell` 拥有一个服务端渲染的统一管理控制台，并为总览、组织、用户、角色与访问权、设备和模型提供常驻导航。控制台继续不含脚本，也不加载外部资产。表单提交到同源服务端路由，因此既有的会话、浏览器同源、CSRF、访问控制和审计检查仍是唯一写入路径；展示层不会引入浏览器 API 或客户端授权状态。

shell 为组织、成员、角色、设备和模型目录管理注册受治理的控制资源。读取与写入路由会在动作不同时询问不同的代码注册权限。部署仍在控制台之外引导首位管理员，随后该管理员通过 `PERMISSION_CATALOG` 组合角色、把角色绑定到用户或解除绑定，并通过受审计的表单管理组织名称、账户状态、设备和模型目录项。

角色页读取类型授权与资源授权。它会创建最常见的组织范围操作——类型授权，并能撤销任一类型。资源专属授权的创建继续留在访问控制服务中，直到 UI 拥有一个不会把显示名与受治理资源 id 混淆的资源选择器。

模型页只存储模型网关的目录字段。凭据字段是服务端凭据引用，而不是密钥材料；Runner 仍只会通过发现流程收到稳定模型引用与显示名。

凭据引用与凭据键寻址的是不同的东西，只有引用能在网关发起调用时解析。控制台与目录各自拒绝不是引用的取值，因此注册会在管理员键入处失败，而不是等到首次调用一个目录读作 active 的模型时才失败。

管理页面或动作失败时，答复说明这是站点的失败。没有这条答复，Web 服务器自带的兜底会回一个空的 400，等于告诉已登录的管理员他们的请求格式有误，而实际无法服务的是站点自身。

## 曾考虑的替代方案

**单独的 SPA 管理应用。** 已否决，因为它会为一个在任何应用包加载前就能工作的界面增加第二套客户端包、API 和授权展示。首批管理工作流需要的是表单与表格，而不是客户端运行时。

**只为既有三个页面加样式。** 已否决，因为外观会改善，但组织、授权、成员角色绑定和公司模型仍然不可见。缺失的信息架构才是产品缺陷。

**让管理角色成为万能钥匙。** 已否决，因为管理账户不应隐含模型调用或知识库访问权。控制台展示并编辑显式授权；它不会在既有的仅 Allow 并集之外加入权限继承。

**让页面接受任意权限字符串。** 已否决，因为封闭目录正是让拼写错误在写入授权处失败的机制。表单只提交目录组合，而服务会再次验证该组合。

## 后果

管理员可以看见 RBAC 已启用、检查某个角色为何准入工作，并在不离开产品的情况下管理当前 Control Plane 已实现的 Team Edition 资源。每次写入都保留与非 UI 调用方相同的审计轨迹和默认拒绝求值。

控制台面向当前单实例、单组织部署，并且不分页地渲染完整列表。账户密码 Enrollment、资源专属授权创建、用户组、知识目录、私有产物目录和生产 PostgreSQL 运维仍是独立能力，而不是伪装成可用管理页面的装饰性占位符。
