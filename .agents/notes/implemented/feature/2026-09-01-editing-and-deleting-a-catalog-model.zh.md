# Agent Note: Editing and deleting a catalog model

Status: implemented

[English](2026-09-01-editing-and-deleting-a-catalog-model.md) | 中文

## 问题

控制台的模型页面只给一行一个控件：停用它，再启用它。一个注册时写错了 Endpoint、写错了上游模型名，或者填了一个解析不出任何东西的凭据引用的模型，只能被关掉。它错误的路由留在目录里，而纠正它意味着以第二个 Ref 注册第二条记录——已经按第一个 Ref 写下的每一条授权都跟不过去。什么都无法把一条记录取走，因此一个组织不再使用的提供方会留下一条永久的记录，以及它背后一个永久的受治理资源。

## 决定

编辑和删除是两件分开的事，而其中只有一件在协议上是新的。

`POST /models` 就是编辑。`ModelGateway.register` 本来就在 `(orgId, modelRef)` 上幂等，并会更新已存储记录的路由列，因此控制台的编辑对话框就是那张注册表单——稳定 Ref 照常显示但不可编辑——提交到同一个地址。记录所持的状态不是路由列，编辑不会动它，因此纠正一个已停用模型的 Endpoint 不会把它放回服务。

`DELETE /models/:ref` 是删除，它触及两个新的服务方法。`ModelGateway.remove` 删掉目录行，然后请访问控制停止治理该模型；`AccessControl.deleteResource` 把受治理资源连同所有指名它的授权一起移除。两者遇到无人持有的 Ref 或 id 都保持沉默，正如 `setStatus` 和 `setResourceEnabled` 已有的做法。这条路由记录为它新增的审计动作 `resource.delete`，与目录已经写下的 `resource.register`、`resource.enable`、`resource.disable` 并列。

`remove` 只解除 `register` 所治理的东西，而这一条是承重的。访问控制会拒绝任何资源行不存在的请求，而控制台自己的模型目录资源——`model.catalog.manage` 正是对它发问的那一个——在同一个 `model` 资源类型下受治理，却不是一条目录记录。路由接受它路径里携带的任何 Ref，因此一次指向那个 urn 的删除，会撤销准入此后每一个 `model.catalog` 请求的授权，把管理员锁在页面之外，且无法从控制台回来。现在，目录中没有对应记录的 Ref 会在触及访问控制之前就返回。

行上的操作变成编辑、停用或启用、删除，三者在没有 `model.catalog.manage` 时都被禁用，且都走控制台其他页面所用的那种对话框。删除对话框说明停用**不会**做什么，因为这两个控件彼此相邻，而它们的差别在于授权。

## Alternatives considered

**再做一个携带路由字段的 `PATCH /models/:ref`。** 否决。`register` 已经在恰好那个身份下存储恰好那些字段，第二次写入要么重复它对 Endpoint 与凭据引用的检查，要么接受它所拒绝的取值。

**允许编辑更改稳定模型引用。** 否决。授权是按 Ref 写下的，一次重命名会把模型从每一个指名它的角色下面悄悄挪走。注册第二条记录才是"这是另一个模型"的诚实说法。

**删掉目录行，留下受治理资源。** 否决，而且这一条正是会悄无声息出问题的那一条：`registerResource` 在 `(orgId, type, externalRef)` 上幂等，因此之后以同一个 Ref 注册的模型会复用那个幸存的资源 id，从而继承被删除模型的授权。

**只要还有角色指名该模型就拒绝删除。** 否决。这会让删除取决于恰好有哪些角色持有授权，把管理员打发到角色页面去逐个寻找，而对一个尚未拿定主意的管理员来说，它买到的东西停用早已提供。

## 后果

`deleteResource` 位于访问控制这一 Capability Seam 上，而不在网关内部，因此下一个需要停止治理某样东西的子系统可以直接使用它。资源 id 从不复用：以同一外部 Ref 再次注册的资源会拿到新的 id 并从零授权开始，而删除正是依赖这个性质。

删除不可撤销，而且会带走授权；确认对话框是管理员与它之间唯一的东西。一个组织想保留但不想提供的模型，正是停用的用途。

控制台没有测试设施，因此这个页面由它下面的 `team-admin-api` 路由测试守住——不动已停用状态的编辑、既不留下受治理资源也不留下资源授权的删除，以及一次指向模型目录资源的删除之后管理员仍能注册模型——Capability Seam 自身的行为则钉在 `model-gateway-sqlite` 与 `access-control-sqlite` 中。
