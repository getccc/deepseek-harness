# Agent Note：登录失败在类型上就不携带原因

Status: implemented

[English](2026-08-29-authentication-tells-nothing-apart.md) | 中文

## 问题

一次登录可能以四种方式失败：登录名不存在、密钥错误、账户被锁、账户被停用。报告是哪一种，是最顺手会去做的事，也是不该交付的事——能区分「无此账户」与「密码错误」的攻击者，可以在攻击任何账户之前先枚举出组织里的全部登录名。

写一句「这几种都显示同一条消息」守不住。它把这个性质放进了散文里，于是下一个表单、下一个错误页、下一行日志，都各有一次破坏它的机会。

还有两个决定必须和它一起做。既然账户存储已经在计数失败，锁定策略该住在哪里？以及，当设计点名 Argon2id、而本仓库不携带任何提供它的依赖时，用什么派生密钥？

## 决策

结果联合类型没有原因字段：

```ts
type AuthenticationOutcome =
  | { ok: true; userId: UserId; mustChangePassword: boolean }
  | { ok: false }
```

调用方没有任何东西可供分支，因此即使界面写得粗心，该性质依然成立。强制它的是类型，不是文档。

计时属于同一个性质，因此属于接口，而不是某一个提供方的备注：`authenticate` 被规定为无论登录名是否存在都消耗相同的可观测时间。密码提供方在没有真实对象可校验时——名字不存在、账户被停用或被锁、账户从未认领过密钥——都对着一个进程级诱饵哈希做派生，因为提前返回的尝试恰好告诉了攻击者那个缺失的原因字段所隐瞒的东西。

**存储负责计数，提供方负责裁决。** `recordFailedLogin` 返回一个数字，`lockUser` 接受一个时刻；多少次算太多、锁多久，是提供方上的配置。锁定会重置计数器，因此一个刚过期的锁不会只差一次失败就再次锁上。

**派生用的是 scrypt，且哈希自己说明这一点。** 已存哈希形如 `$scrypt$N=..,r=..,p=..$salt$derived`：校验按哈希所记载的内容分派，而绝不按当前配置；一次针对较弱参数的成功登录会按当前参数重新派生。因此提高成本会在每个持有者下次登录时迁移其账户，而日后加入的 Argon2id 提供方是增量式的、不需要切换日——认不出的算法读作「需要替换」，而不是读作匹配。

这一点刻意偏离了设计中的 Argon2id：Argon2id 需要本仓库并不携带的依赖，而 scrypt 内置于 Node 且是内存困难的。自描述格式正是让这次偏离易于撤销的原因。

## 曾考虑的替代方案

**保留原因字段，并规定由 UI 收敛它。** 已否决：那把一个安全性质挪进了散文，而未来每个调用方都能独立违反它。仓库自己的规则是：在做出决定的那个操作里强制该决定。

**只把原因交给审计。** 目前否决：审计尚不存在，为一个没有消费方的第二通道预留是投机。审计落地时会读取存储自身的计数器。

**把锁定策略放进存储。** 已否决：那样一来决定的就是存储，而第二种认证方式会继承密码方式的阈值。计数是存储的事，裁决是认证的事。

**引入 Argon2id 依赖。** 在本次改动中否决：原生模块会让打包后的 CLI 变复杂，而 WASM 版本对一个安全原语来说仍是一个新依赖。在格式已经留好门的前提下，两者都不必要。

## 后果

在没有新机制的情况下，任何东西都无法区分登录失败，包括那些出于正当理由想区分的。日后若要「您的账户已被锁定」这样的消息，需要一条单独、经过刻意设计的通道，而不是在此处加一个字段。

限流只在账户级。本接缝看到的是登录名与密钥，看不到来源地址或浏览器会话，因此把尝试分散到许多账户上的攻击者不会被拖慢。那属于 HTTP 入口，而它尚不存在。

提供方的派生成本默认偏慢，调低它是部署需要明确做出的配置决定。测试跑在刻意调低的成本上，这也是它们断言策略而非硬度的原因。
