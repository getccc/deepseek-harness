# Agent Note：账户存储只保存身份，别无其他

Status: implemented

[English](2026-08-29-account-store-seam.md) | 中文

## 问题

Team Edition 必须先有地方保存「成员是谁」，才谈得上保存「成员能做什么」。有两个问题必须一起回答，因为其中任一个答错，都会把另一个锁死。

第一个是存储拥有什么。把密码材料放进账户记录是最顺手的形状，也正是让日后替换登录方式变昂贵的那个形状：外部身份提供方届时面对的，将是一张其列结构已经编码了「认证就是密码」这一假设的表。

第二个是用哪个数据库。目标部署是单个 Control Plane 实例，但设计中点名了 PostgreSQL，而本仓库没有任何数据库驱动——引入一个就意味着同时引入驱动依赖、迁移工具，以及一套「测试跑起来之前数据库必须先存在」的测试策略。

## 决策

`dsh-account-store` 是接缝：组织、成员账户，以及锁定策略要读取的计数器。它是一个仓储。它记录发生了什么、把冲突报告为具名错误，自身不做任何决定——五次失败是否意味着锁定、编码后的哈希里装着什么，都属于经它读写的认证提供方。

认证材料只能经由 `getPasswordHash` / `setPasswordHash` 触及，从不出现在账户记录上。存储把该值当作不透明字节：不解析、不比较、不从中派生任何东西。这正是让存储与认证方式保持正交的原因，于是替换密码登录改变的是挂载了哪个提供方，而不是存了什么。

`dsh-account-store-sqlite` 是随附后端，基于 Node 内置的 `node:sqlite`——它已经是 session persistence、session query 和 storage 的后端，因此没有给仓库新增任何驱动。

**这一点刻意且可逆地偏离了设计中的 PostgreSQL 选择。** 它所面向的部署是一个 Control Plane 实例，在那里 SQLite 的单写者限制并不构成约束；PostgreSQL 的成本要在被明确推迟的多实例部署中才换得回价值。PostgreSQL 后端是同一个 Service Definition 之后的第二个 provider，而此处的实体模型正是设计所规定的那一套，因此日后写它是实现一个接口，而不是重开一次决策。

### 两条值得点名的契约

每个方法都返回 promise，因此**没有任何方法同步抛出**——调用方的 `.catch` 必须能看到每一种失败。这些方法保持同步的函数体并返回 `Promise.reject`，而不是写成 `async`，因为仓库的 lint 拒绝没有 `await` 的 `async` 函数。测试守住了这一点：它们断言的是 rejection，而同步抛出并不满足。

`listUsers` 按 SQLite 的行标识排序，而非 `created_at`。同一毫秒签发的两个账户共享同一个时间戳，而时钟回拨会让它们的顺序出错；插入顺序才是「创建顺序」的含义。

## 曾考虑的替代方案

**把密码哈希放在账户记录上。** 已否决：它把「认证就是密码」编码进了已存储的身份，而这正是双接缝拆分要避免的耦合。该列仍按设计的数据模型留在账户行上，但只有认证提供方读写它。

**现在就引入 PostgreSQL 驱动。** 在本次改动中否决：它一次性决定了驱动、迁移工具和测试基础设施策略三件事，而部署目前一件都不需要，且在没有数据库的环境中一件都测不了。

**只为测试准备的内存后端。** 已否决：一个只为测试而存在的后端，证明的是接缝对着某个没有任何部署会运行的东西能工作。SQLite 后端在测试里跑 `:memory:`、在生产里跑文件，因此测试演练的是真正交付的代码。

## 后果

部署得到持久化的账户，且无需运维任何数据库。当多实例到来时，它需要一个 PostgreSQL provider 和一条迁移路径——`SCHEMA_VERSION` 为 1，打开时会拒绝更新的文件，但尚无任何东西升级更旧的文件，第一次 schema 变更必须补上它。

账户只能停用、不能删除，因为角色、设备和审计行都将引用它们。删除路径需要先定下这些引用如何处理。

存储可以容纳多个组织，但尚无任何东西负责解析一个请求属于哪个组织，因此在请求级组织解析出现之前，部署只使用一个。
