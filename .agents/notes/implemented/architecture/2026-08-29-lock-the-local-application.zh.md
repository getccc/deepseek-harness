# Agent Note：锁定本地应用是一次导航，不是一次 RPC

Status: implemented

[English](2026-08-29-lock-the-local-application.md) | 中文

## 问题

`dsh web` 是前台工具：关掉它，浏览器的访问权随进程一同结束。而 Team Runner 是长期运行的后台服务，于是同一个人现在拥有一个只要机器开着、就一直在已知端口上可达的本地应用。离开共享或无人看管的机器时，除了停掉服务别无办法，而停服务同时也会中断正在进行的工作。

结束一个浏览器会话意味着让承载它的 cookie 过期。这只能在 HTTP 响应中表达，因此没有任何 RPC 方法或人类命令能做到：两者都在会话中作答，而不在持有该 cookie 的那条线路上。

## 决策

`client-connection` 在其 `/api` 前缀之外注册一条精确的 `/lock` 路由。携带有效会话的 `GET` 或 `HEAD` 会得到一个把同一 cookie 置为过期的响应；其他任何方法返回 405。

该路由只用于导航。它不承载 RPC、不读取请求体、不触及任何 Host 能力，因此它位于 `/api` 前缀之外，也位于守卫 `/api` 的浏览器信任 fence 之外——那里没有任何东西需要 fence 去守。

真正保护它的是 cookie 自身的 `SameSite=Strict`。只有已认证的请求才会清除任何东西，而由其他站点发起的导航不会携带该 cookie，因此被读作未认证，会话原封不动。同站导航——也就是本人选择锁定自己的应用——会携带 cookie 并将其清除。这道防御是 cookie 本就具备的性质，不是新增的检查。

`BrowserAuth` 现在完整拥有它此前只承担一半的会话生命周期：签发（`authorizeIndex`）、校验（`isAuthenticated`）、结束（`lock`）。

用于清除的 cookie 重述了签发时的名称、`Path`、`HttpOnly` 和 `SameSite`。浏览器只有在这些都匹配时才会替换一个 cookie，因此任何属性漂移都会让原 cookie 留在原处、悄无声息地锁不掉；测试因此把它们与签发的 cookie 对比，而不是与字面量对比。

## 曾考虑的替代方案

**通过 `ctx.commands` 提供人类命令。** 已否决：命令在会话内部作答，无法在浏览器的连接上设置响应头。它至多只能请浏览器导航到这里——那就是本路由再加一层间接。

**锁定时轮换签名密钥。** 已否决：那会结束本 Runner 签发的每一个浏览器会话，包括此人仍然需要的其他机器上的会话。一次性结束全部是刻意更重的动作——删除 owner 凭据记录并重启——保持它更重正是要点所在。

**要求 `/lock` 通过信任 fence。** 因归类错误而否决：fence 的存在是为了阻止跨站页面经 `/api` 触及 Host 能力。本路由不触及任何能力，而跨站这一情形已由 `SameSite=Strict` 不携带 cookie 所回答。

## 后果

两处断言 `client-connection` 只注册一条路由的测试，现在指名它注册的那两条。路由数量是本包可观测表面的一部分，因此断言随之改动，而不是被放宽成一个下限。

锁定是按浏览器计的。在两个浏览器中打开应用的人必须分别锁定，README 对此明确说明，而不是让人以为 `/lock` 是一次全局登出。

该路由可以通过手输 URL 到达，这是刻意的：它在任何 Team UI 出现之前就能用，而客户端中后续的锁定控件只是指向它的一个链接，不是新机制。
