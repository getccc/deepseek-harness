# Agent Note: Team Runner 负责成员登录

Status: implemented

[English](2026-08-30-team-runner-owns-member-sign-in.md) | 中文

## 问题

Team Runner 与 Control Plane 面向的是不同人群。普通成员在回环地址上的 Runner 中工作，管理员则使用 Control Plane 创建账户、组合角色、绑定授权、停用成员、撤销设备并管理公司资源。让普通成员从 Runner 跳到 Control Plane 登录，会把管理端源变成成员产品的一部分，违背这层分工。

独立 Web 应用还通过进程 Token 解锁。如果 Team 复用这项启动行为，就会绕过访问控制所评估的组织账户，因此 Runner 必须先拥有自己的入口，再开放应用。

## 决策

**Team Runner 在 `/team/login` 提供账户密码表单。** 它的启动入口是干净的本地 `/team/open` 路径，不携带独立 Web 所用的进程 Token。未解锁的浏览器会被送到本地表单；已通过本地认证的浏览器直接进入应用。该流程不包含任何普通成员到 Control Plane 的导航。

**应用前表单与应用内账户入口属于同一个本地功能。** 服务端渲染表单拥有自己的响应式双语登录界面，因为此时 React 应用仍处于锁定状态。进入应用后，同一个包通过可选的 `settings.launcher` Slot 替换普通设置入口：侧栏展示成员身份，其菜单可以打开既有设置面板，或导航到本地退出路由。该路由会忘掉进程凭据、让已认证的浏览器 Session 过期，并直接返回 `/team/login`。设置 Shell 继续拥有面板状态与各分区。

**密码仍会经配置好的源送达 Control Plane。** 本地页面不验证也不存储密码。`team-account-client` 开启一个设备 Transaction，把登录名、密码与该 Transaction 一起发给 Control Plane 面向 Runner 的端点，再用 PKCE Verifier 和设备密钥签名兑换返回的一次性 Code。除本地开发外，部署必须在外层用 TLS 保护这个源。

**本地表单会在读取密码前证明其浏览器源。** 普通 `Origin` 必须匹配 Runner authority。`Referrer-Policy: no-referrer` 可能让浏览器发送 `Origin: null`；只有同时携带由浏览器控制的 `Sec-Fetch-Site: same-origin` 时才会被接受，缺失分类或跨站分类都会被拒绝。

**每次成功登录都会创建新的设备凭据族。** 同一物理密钥再次绑定时，会在签发新凭据前撤销旧凭据族。这可以阻止旧 Token 通过可变的设备行观察到后续账户归属。

**本地登录成功后，只有公开成员身份会返回 Runner。** Control Plane 的登录响应在一次性 Code 旁提供登录名与显示名。Runner 将这两个字段与设备凭据一起保存，在刷新时继续保留，并且只通过 `/team/account` 向已认证的本地浏览器 Session 暴露它们。密码、设备密钥、刷新 Token 与访问 Token 都不会进入浏览器响应。

**Control Plane 浏览器应用是管理表层。** 仅有密码认证不足以创建管理会话；账户还必须持有 `organization.admin.access`，后续每次管理请求也会先重新检查该权限，再检查具体动作的授权。默认 Control Plane 组合不再包含成员确认页面。

**账户状态参与每一次访问决策。** 不存在、跨组织或已停用的 Principal 即使仍有角色绑定和设备 Token，也会得到 `default-deny`。因此停用成员会在授权点立即终止其公司资源使用；系统不依赖等待 Token 过期。

本决策取代[较早的 Handoff Note](2026-08-30-the-handoff-is-navigation-not-a-tunnel.zh.md)所述公司站点导航流程，成为默认 Team 组合。旧 Handoff 包在预发布过渡期间保留为未组合的可选包；它的 Callback 细节不再描述随产品交付的成员入口。

## 曾考虑的替代方案

**继续在 3095 上认证成员，登录后再隐藏管理控件。** 已否决，因为普通成员仍然能够看到并依赖管理端源，而且认证仍与一条不归 Runner 所有的浏览器路由耦合。

**让浏览器 JavaScript 把密码直接发给 Control Plane。** 已否决，因为这需要跨源浏览器策略，并会向普通成员客户端暴露管理端源。Runner 已经拥有设备密钥与绑定协议，因此也应拥有认证调用。

**让浏览器从 Control Plane 读取成员名称。** 已否决，因为这会让侧栏依赖跨源管理端，并引入第二套浏览器认证机制。Runner 已在本地登录时收到权威身份，可以在既有本地 Session 下暴露两个显示字段。

**把账户控件放在设置入口旁边。** 已否决，因为两个底部控件会重复设置入口，也不符合账户菜单交互。可选 Launcher Slot 让 Team 只替换入口，同时保留设置面板与所有已贡献分区。

**管理员停用账户后，仍把有效设备 Token 当作充分条件。** 已否决，因为账户状态是由管理员控制的授权输入。等待 Token 过期会形成一个时间窗口：控制台显示成员已停用，网关却仍然准入。

## 后果

部署需要把同一个组织 ID 同时提供给 `team-control-plane-http` 和 `team-admin-api`。前者把它用作成员账户命名空间，后者把它用作管理命名空间。任一值都不会被猜测，缺失时启动失败。

默认 Profile 的边界会直接体现在浏览器中：普通成员使用 3090，管理员使用 3095，独立 `dsh web` 则继续在 3080 使用进程 Token 解锁。除了应用权限检查之外，3095 的网络隔离仍由部署负责。

一个 Runner 进程仍只持有一份活跃团队凭据。再次登录会为使用该进程的所有浏览器替换这份凭据。每浏览器多账户需要不同的凭据保管设计，不属于本次改动所作的承诺。

可选的浏览器 Handoff 绑定不会经本地登录响应进行认证，因此它可以持有不含成员显示字段的设备凭据。在这种组合中，Launcher 使用中性的团队成员标签，同时保留设置与退出操作。
