# Agent Note：一个覆盖权限目录的角色，以及管理员可以拿走什么

Status: implemented

[English](2026-08-31-a-role-that-covers-the-permission-catalog.md) | 中文

## 问题

[导航那篇 Agent Note](../feature/2026-08-31-navigation-is-data-and-menu-access-is-a-grant.zh.md) 往目录里加了六项权限。在已经跑着的部署里，它们所把守的每一个控制台控件都失效了：它的管理员角色持有三十九对中的三十五对，而缺的四项——`department.manage`、`member.update`、`role.update`、`role.delete`——恰好就是管理员反馈"点不了"的新增、删除与编辑按钮。

这不是某一个部署的失误。授权是存储下来的行，因此角色只持有它被授予过的东西；而权限目录由代码播种，因此它随每一次构建增长。于是每一次治理了新事物的构建，都会把管理员挡在新事物之外，而唯一的回路是手工指名这些新配对——通过一个一次只能加一项、从四十个字符串的平铺列表里挑选的弹框。

同一个问题的另一半，是管理员根本做不到的事。账户只能停用、不能删除，于是用户目录会不断累积没人能移除的行。

## 决定

**一个角色可以被标记为覆盖目录，并由 Control Plane 保持这一点为真。** `Role.coversCatalog` 表示该角色持有本构建治理的每一项权限；`AccessControl.syncCatalogRole` 补齐它欠缺的配对，管理 API 在进程启动时为其组织内每个被标记的角色运行它。这些授权是真实的行而不是通配符，因此评估仍是原来那套——默认拒绝、角色的授权允许——而一次决定依然可以通过指名产生它的那条授权来解释。

这次同步只增不减。目录不再命名的配对留在原处，因为那条授权可能仍是某件事能work的原因；而一次什么都没授予的启动不会写审计行：该角色允许什么，没有发生变化。

**Schema 迁移会标记系统角色。** 在这个列存在之前，部署的 bootstrap 以 `kind: 'system'` 创建它的管理员，并手工授予它整个目录。在加列时一次性标记这些角色，能让那份意图跨越升级继续生效，而不是要求每个既有部署自己去发现缺了哪四项授权。从此以后创建的角色，只有在有人要求时才会被标记。

**标记一个角色属于授权管理，而不是编辑。** 该路由像对待其他字段一样在 `role.update` 之下接受 `coversCatalog`，并在请求携带这个字段时额外要求 `role.grant.manage`——因为这个字段会扩大角色允许的范围，而其他字段只改变它如何被阅读。

**一个角色的权限以集合的方式设置，来自一棵树。** `POST /roles/:id/permissions` 让角色的类型授权恰好等于传入的那些配对：勾选即授予，取消勾选即撤销。针对单个具名资源的授权不在这个列表里，也不会被改动——一个目录编辑器不得悄悄丢弃它没有展示的东西。控制台把这个弹框与菜单权限都渲染为可勾选的树，目录按资源类型分支，导航按它自己的上级分支，而后者正是管理员已经在菜单页面读到的那棵树。

**账户可以被删除。** 由 `member.delete` 把守。Store 移除账户以及它持有的浏览器会话，并让它曾领导的部门失去负责人，而不是把部门与人一起删掉。路由会先解绑该账户的角色、吊销它绑定过的电脑，因为一条指向已消失账户的绑定或凭据，会允许无人可追溯的工作。审计行保留：它们是该账户做过什么的历史，而历史不会随它离开。管理员不能删除自己正在使用的账户，那会终结正在执行这次请求的会话。

## 曾考虑的替代方案

**由鉴权短路的超级管理员。** 已否决，因为那恰恰是这套评估所没有的东西。`AccessDecision` 会指名允许该请求的那些授权，而通配符是在没有可指名之物的情况下允许；于是每一次解释、每一次审计阅读、每一个"他们凭什么能做这件事"的回答，都会多出一个特例。把授权实体化，能让故事只有一个。

**永久把 `kind: 'system'` 当作覆盖目录。** 已否决，因为系统角色的含义是产品随附、无人可删，而不是它持有一切；一个日后随附了受限系统角色的部署，会在升级时被悄悄扩权。迁移只用 `kind` 一次，用来读出本就存在的意图，此后由显式标记承载。

**在启动时重跑部署的 bootstrap 脚本。** 已否决，因为 bootstrap 会创建组织与管理员，而一次启动不得做这两件事之一。需要保持当前的是某一个角色的授权，而这正是 API 所要求的。

**不提供删除账户。** 在[导航那篇 Agent Note](../feature/2026-08-31-navigation-is-data-and-menu-access-is-a-grant.zh.md) 里以"账户是审计记录的锚点"为由记为否决。那个理由针对的是审计行，而它成立——审计行确实保留。但它并不涉及账户行本身，而账户行没有其他东西需要：一个只增不减的用户目录，不是管理员能维护的用户目录。

**在新的集合编辑器旁边保留"添加一项权限"。** 已否决，因为两个写同一批授权的控件，对"取消勾选意味着什么"会给出不一致的答案。树展示角色持有什么，并写入它所展示的内容。

## 结果

持有 `role.grant.manage` 的管理员可以一次操作就把角色补齐到目录，而被标记为覆盖目录的角色再也不会落后于某次构建。从更早 Schema 升级上来的部署，会在下一次启动时发现它的管理员角色已被标记且完整，并有一条审计行指明这次启动授予了什么。

访问控制的 `SCHEMA_VERSION` 推进，新增 `covers_catalog` 列与上述一次性回填。权限目录新增 `member.delete`，因此以指名权限的方式绑定角色的部署需要加上它，相应控件才会出现——除非该角色覆盖目录，而这正是重点所在。

删除是控制台提供的唯一不可逆操作。它只拒绝当前登录的账户：把倒数第二个管理员删掉，仍然可能让一个组织没有任何管理员，而控制台不会察觉这一点。
