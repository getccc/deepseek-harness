# Agent Note：Team Control Plane 是独立树，因此无法执行代码

Status: implemented

[English](2026-08-29-control-plane-carries-no-local-execution.md) | 中文

## 问题

Team Edition 的 Control Plane 持有全部公司凭据，并应答每位成员 Runner 的请求。如果它同时还能在自己所在主机上执行代码、读取文件或驱动 Agent，那么攻破它就等于同时拿到凭据和持有这些凭据的服务器上的 shell。

最顺手的组合方式正是其他每个 Team 配置行采用的那种：叠加在 `dsh-base` 之上再添加公司服务。但在这里那是错的，因为 `dsh-base` 恰恰就是挂载 Agent loop、本地文件系统、subprocess、shell 和 sandbox 提供者的那个 bundle。叠加它会一次性把这些全都交给 Control Plane，而配置树中没有任何东西会指出这并非本意。

缺席本身也难以长期守住。一个缺失的能力，看起来和一个还没人添加的能力完全一样，因此后来的配置行可以重新引入某项能力，而任何评审者都不会注意到它越过了哪条边界。

## 决策

`@deepseek-ai/dsh-team-control-plane` 是形态与 `dsh-sdk-minimal` 相同的独立 bundle：它的 insert 列表就是完整的 Cordis 树，不叠加在 `dsh-base` 之上。`team-control-plane` profile 模板只指名这一个 bundle，别无其他。当前阶段这棵树只有一行绑定回环地址 `3095` 的 `webserver`，与 Team Runner 的 `3090` 和 `dsh web` 的 `3080` 都不同。

这种缺席是组合层面的事实而非运行时事实——那里没有任何东西可供观测——因此由测试在三个相互独立的位置守住：

| 屏障 | 位置 | 拦住什么 |
|---|---|---|
| patch 不指名任何本地执行包 | 本 bundle 的测试 | 向树中新增的配置行 |
| 清单不声明这类依赖 | 本 bundle 的测试 | Loader 无法解析从未声明过的裸插件标识 |
| profile 模板不指名携带它们的 bundle | `app-boot` 的 profile 测试 | 通过叠加 `dsh-base` 一次性重新引入整组能力 |

禁用集合是逐个包写出的，而不是按前缀匹配。前缀会悄悄吸收一个新的能力包，或让某个包因名字在模式之外而悄悄逃过；显式清单则迫使添加能力包的人在此处做出决定。

## 曾考虑的替代方案

**叠加 `dsh-base` 后禁用不需要的行。** 已否决：一个 `disabled` 的行距离被重新启用只有一层 patch 之遥——部署方自己的 profile patch 就能做到，而没有任何测试拦在中间。根本不挂载该 bundle，比挂载后再关掉是更强的保证。

**按前缀匹配禁用包。** 出于上述理由否决：它对模式之外的名字失效开放，对模式之内的无关名字失效关闭，无论哪种都消解了那个刻意的决定。

**用运行时不变量断言这些服务不存在。** 已否决：没有可观测的权威关系。伴随插件保持为空并按包不变量规则记录该理由。

## 后果

每一项公司服务——账户、RBAC、配额、审计、模型与知识库网关、私有目录、管理界面——都插入这同一个 patch 文件，且必须让三道屏障继续通过。确实需要运行子进程的服务不能悄悄放松它们；那需要它自己的 Agent Note。

该保证约束的是本仓库交付的内容，不是运维方后续组合出的内容。若部署方在自己的 profile patch 中添加本地执行配置行即可绕过，这里的任何测试都无法阻止。

在公司服务落地之前，该 profile 启动的是一个不注册任何路由、对每个请求返回 404 的服务器。这正是预期状态：边界先于放进它里面的任何东西存在。
