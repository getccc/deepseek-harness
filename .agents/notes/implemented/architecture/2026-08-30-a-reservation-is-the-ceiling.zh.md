# Agent Note：预留就是上限，而结算只发生一次

Status: implemented

[English](2026-08-30-a-reservation-is-the-ceiling.md) | 中文

## 问题

一次公司模型调用花的是属于组织的钱，而这笔支出发生在这个 Control Plane 控制不了的上游 Provider 处。从"决定发起调用"到"知道这次调用花了多少"之间，可能发生四件事：Provider 带着 Usage 回答、成员取消、Provider 拒绝，或者根本没人知道结果——进程崩了、连接断了、响应到了却没有 Usage 字段。

一个只有"计费"和"不计费"的账本，在其中大多数情况下只能猜，而无论朝哪边猜，总有一处是错的。往低猜，会让一个崩溃循环花掉组织的预算却没有留下任何记录。往高猜，则是为没有任何 Provider 执行过的工作向成员收费。

底下还有一个更尖锐的版本。有两样东西会结算同一个请求——完成时的调用方，以及请求跑得太久时的 Reconciler——而对于一个双方都看不到结局的请求，它们可能都是对的。如果两者都能写入，一个请求就会被计费两次。

## 决策

**预留就是一个请求所能花费的上限。** 它在上游调用之前持有输入 Token 加上该请求可能产生的最多输出。此后每一次结算都被它封顶：Provider 报告的数量超过该请求被允许产生的量，或者估算值超出，都按实际持有的数额计费。没有这个封顶，估算就是凭空发明；有了它，估算最差也不过是组织早已同意去承担的那个数额。

**结算只发生一次，而说了算的是数据库。** 结算表的主键就是 Reservation，因此第二条结算根本插不进去。对一个已结算的 Reservation 再次结算，返回的是既有记录，不改变任何余额——正是这一点让调用方在崩溃后重试是安全的，也让 Reconciler 与它并行运行是安全的。

**三种结算类型，因为它们回答的是日后不同的问题。** `reported` 是账单可以对账的对象。`estimated` 是在没有证据的情况下所计的费，被标记出来以便对账时找到它。`released` 是组织从未被收费的部分，也是唯一会整份归还预留的结果。

**`released` 需要上游拒绝了该请求的证据。** 也就是 Provider 自己产出的、说明这一点的响应——一个没有生成任何内容的状态。一次完全没有响应的传输失败**不是**拒绝的证据：Provider 可能已经处理了 Prompt 并生成了没人看到的 Token。那种情况属于 `estimated`，也就是设计中的"不确定"路径。

**过期的 Reservation 被结算，而不是被释放。** 一个跑过了自己窗口的请求，花掉了预算的可能性远大于什么都没花，而一个会释放的 Reconciler 会让崩溃循环无上限地花费却什么也不记录。Reconciler 按预留额计费并把记录标记为 `reconciled`，于是日后的读者能区分"没人报告过的一笔计费"和"有人报告过的一笔"。

**没有限额就没有上限。** 一个管理员没有设限的组织，不会被悄悄限制为零。`availableTokens` 是缺席而不是零，因此调用方不会把"无限"误当成"已耗尽"。

**每一个余额都是推导出来的，从不存储。** 已结算 Token 是各笔结算之和；已预留 Token 是尚无人应答的各笔 Reservation 之和。一个存储的运行总额会成为真相的第二处住所，而两者最终会以只有审计才能发现的方式彼此不一致。

## 这个账本不决定什么

它不决定谁可以使用某个模型——那是[访问控制](2026-08-29-access-control-evaluation.zh.md)。它也不知道"一个月"是什么：由部署为自己的周期命名，调用方询问某个请求所属的那一个，这让日历、时区和账期都留在了一个唯一职责是做算术的账本之外。

它计的是 Token，不是钱。按价格加权需要模型目录所拥有的价格元数据，而一个凭空猜出换算关系的账本，会以货币为单位地出错。

## 曾考虑的替代方案

**请求失败时释放预留。** 作为默认行为已否决：大多数失败无法与"Provider 已经服务过的请求"区分开，而其失效模式是无上限的花费，且不留下任何记录。

**让结算按 Provider 报告的数量计费。** 已否决：那会让预留沦为建议。一个报告数量超过该请求被允许产生量的 Provider，会花掉从未被任何预留声明过的预算，而当初判定该请求负担得起的那次算术，算的是另一个数。

**存储一个运行余额。** 已否决：它更快，而且是真相的第二个来源。求和发生在已按组织与周期建立索引的行上，而此处的正确性比那次读取更值钱。

**一种结算类型加一个布尔 "estimated" 标记。** 已否决：`released` 不是"估算为零"，而是"什么也没花"这个陈述，把它们合并会丢掉账单对账所需要的那个区别。

**让 Reconciler 删除过期的 Reservation。** 已否决：那一行正是"预算曾被持有、以及为何被持有"的证据。对账写下的是一条结算，那是一份记录；删除则是一份记录的缺席。

## 后果

`reservationTtlMs` 限定一个崩溃的请求最长能占住多久预算。它应当高于部署所预期的最慢一次完成，且不能贴着它：过低会让一个慢但活着的请求在仍在运行时就被按上限计费，过高则会让一个已崩溃的请求占住预算那么久。

一笔经 Reconciler 的结算按整份预留计费。对于一个确实很早就失败了的请求，这是多收了，而 `estimated` 标记正是让它可被找到的东西——账单对账可以退回差额，而这个账本刻意不去尝试这件事。

这里没有任何东西写审计记录。设计要求在对账时写一条，而执行对账的调用方才是知道主体与关联标识的那一方；补上它属于那个将按计划运行 Reconciler 的网关。
