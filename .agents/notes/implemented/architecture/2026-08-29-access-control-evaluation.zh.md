# Agent Note：授权靠拒绝表达力来保持可解释

Status: implemented

[English](2026-08-29-access-control-evaluation.md) | 中文

## 问题

Team Edition 治理模型、MCP Server 与 Tool、知识库 Scope、插件、Skill、成员、设备和用量。表达「谁可以碰什么」最顺手的方式是一门策略语言——条件、deny 规则、继承——而其中每一项特性都会让同一个问题更难回答：这一个请求究竟为什么被拒了？

这个问题不是学术性的。排查成员访问权的管理员、解释一次拒绝的审计行、以及一次客服对话，都需要它。策略引擎靠重放求值来回答；一份授权清单靠被读出来回答。

随之而来的还有两个较小的决定。权限可以是数据库接受的字符串，那会让一个拼写错误变成一次无声的错配。授权也可以携带资源的 URL 或凭据，那会让轮换其中任何一样变成一次授权迁移。

## 决策

求值只有四条规则，别无其他：默认拒绝；角色的授权准入；多个角色取并集；被停用的资源无论任何授权怎么说都被拒绝。没有显式 Deny、没有角色继承、没有表达式语言。因此一个决定会返回准入它的那些授权，而解释一次准许就是把它们列出来。

管理角色不是万能钥匙。`member.create` 不会带来关于模型的任何权限，因为每一项权限都必须被显式授予，持有另一项并不隐含任何东西。

**权限是代码中的值。** `PERMISSION_CATALOG` 是一个封闭的 `(resourceType, action)` 集合；管理员用它拼装角色，无法凭空造出权限字符串。SQLite 后端把该目录播种进一张表，并让两张授权表用外键指向它，因此即使某个调用方绕过服务直达数据库，指名未受治理组合的授权也存不进去——该检查同时存在于做出决定的那个操作里**和**保存它的那份存储里。

**授权按引用指名资源。** 资源行以 `(组织, 类型, 外部引用)`——也就是请求所指名的身份——作键，并配一个供授权指向的代理 id，于是显示名可以变、URL 或凭据可以轮换，而不必触碰任何一条授权。注册是幂等的，因为拥有方子系统在每次启动时都会重新注册自己的目录。

**用户组批量绑定，不改变任何结果。** 求值把直接角色与经组派生的角色并成一个集合，因此用户组是管理员的便利，而不是算法知晓的第二种绑定。两种途径都持有的角色只计一次。

**只有一个修订号计数器，不是每个子系统一个。** 每一次可能改变结果的变更都会递增组织的 `policyRevision`，它随组织存放在账户存储中，而一个决定会引用它据以计算的那个修订号。这正是让缓存能区分「陈旧」与「仅仅是旧」的依据。治理一个资源同样会递增它，因为某个角色已持有的类型授权现在多覆盖了一样东西；创建用户组则不会，因为它什么都没绑定。

### 有一个名字已经被占用

设计把请求与答案称作 `AuthorizationRequest` 和 `AuthorizationDecision`。这两个名字在本仓库中冲突：credentials 子系统已经用 `AuthorizationRequest` 表示 OAuth 式的授权流请求，那是穿着同一个词的另一个概念。此处改为 `AccessRequest` 与 `AccessDecision`，于是 authorization 继续表示凭据流，而权限检查也读起来就是权限检查。

## 曾考虑的替代方案

**一门策略表达式语言。** 已否决：它换来的是无人要求过的条件，付出的是「靠读数据来解释一次拒绝」的能力。如果某个条件确实变得必要，它应当以一条具名、有测试的规则的形式到来，而不是一个通用求值器。

**显式 Deny。** 已否决：在只有 allow 的授权模型下，一个决定就是并集，顺序与优先级永远不会进入答案。Deny 会让两者成为每一次解释的一部分。

**角色继承。** 出于同样的理由否决：继承来的授权是读者必须重建、而非直接读到的东西。

**权限作为自由字符串。** 已否决：一个拼写错误会变成一条永远悄悄匹配不上的授权，或者更糟——在该字符串日后被启用时匹配上某个并非本意的东西。

**把 endpoint 或凭据存在授权上。** 已否决：那会让轮换变成迁移，并把密钥放进管理员会编辑的表里。

## 后果

每一项新的受治理能力都会往代码目录里增加一个 `(resourceType, action)` 组合，而升级中的部署通过 schema 的播种拿到它。让一个组合退役时，那一行会留在数据库里以便既有授权保住外键；阻止它被再次授予的是代码目录。

一次拒绝会区分 `default-deny`（根本没有角色）、`no-grant`（有角色但没有匹配的，或没有这个资源）和 `resource-disabled`。最后一个刻意确认了资源存在，因为它回答的是一个确实持有授权的主体，而一条令人困惑的消息比这点披露更糟。

没有任何东西缓存决定。修订号的存在正是为了让调用方能安全地缓存，而在服务内部加一个缓存，会让同一个答案背后出现两个权威。
