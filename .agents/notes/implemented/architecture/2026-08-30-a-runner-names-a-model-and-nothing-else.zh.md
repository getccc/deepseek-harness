# Agent Note：Runner 只指名一个模型，别无其他

Status: implemented

[English](2026-08-30-a-runner-names-a-model-and-nothing-else.md) | 中文

## 问题

公司模型正是 Control Plane 需要持有凭据的原因，而凭据绝不能到达成员的电脑——否则一个与 Runner 共享进程的插件，就能读到一把为整个组织计费的钥匙。

显而易见的形态是一个代理：转发 Runner 发来的任何东西，并在出去的路上附上凭据。它以一种容易被忽略的方式失效：只要 Runner 提供了调用*去往何处*的任何一部分，凭据就会一同去往那里。一个 URL、一个 Host、一次 Path 覆盖、一项 Proxy 设置、一个上游 `Authorization` 头——每一样都是把公司凭据指向公司未曾选择之处的途径。

同一个问题在请求体内部还有第二个版本。一个被授权使用廉价模型的 Runner，可以在请求体里写下一个昂贵模型的名字，而一个原样转发请求体的代理，会忠实地为那个没人授权过的模型向组织计费。

## 决策

**Runner 指名一个模型，而不提供任何关于调用去往何处的信息。** Endpoint、上游模型名和凭据引用全都来自目录。请求里根本没有让 Runner 放进地址的地方，因此没有什么要剥除、也没有什么要校验——那些事实压根不属于 Runner 所发送的内容。

正是这一点让凭据隔离成为结构性的。它不是靠删掉危险字段来强制的；那些字段并不存在。

**网关覆盖决定这次调用花多少的那两个请求体字段。** `model` 变成目录里的上游名，因此一个"指名了一个模型、却在请求体里写了另一个"的 Runner，到达的是它被授权的那一个。`max_tokens` 或 `max_completion_tokens` 在**请求体已经携带它时**被预留上限封顶——添加一个 Adapter 没有发送的上限，会改变它本意要发的请求。

其余一概不动。Runner 发送的是它自己的 LLM Adapter 构造的请求体，因为在 Control Plane 里重新实现每个 Provider 的请求格式，等于多出第二个需要维护正确性的 Adapter，而两者最终会漂移。

**目录持有的是凭据引用，不是凭据。** 密钥存放在 Credential Provider 中，并在调用发生的那一刻被解析，因此轮换不改变目录中的任何东西，读取目录也得不到任何人能花掉的东西。

**稳定 Ref 就是身份。** `modelRef` 是 Runner 所索取的、也是授权所指名的，而它永不移动；Provider 自己的称呼放在它旁边，并可以在它之下改变。Provider 在上游重命名一个模型，改的是一列，而不是每一条授权。

**注册一个模型即在同一次调用中纳入治理。** 一条访问控制不知道的目录记录，是一个没有授权能指名、也没有人能调用的模型；而添加了它的管理员将必须知道要去别处再做第二件事，第一件才有意义。退役同时移动两者，因此一个被撤下的模型无论请求从哪个入口到达都会被拒绝。

**三个判定，按这个顺序。** 有没有这个模型——"不存在"和"无授权"被同样地回答，因此一次拒绝永远不会告诉成员某个组织有哪些模型。这个主体可不可以调用它——在每一次调用上、对照当前策略修订号询问，因此角色变更在下一次请求就生效，而不是等 Token 过期。还有没有预算——放在最后，因此一个被拒绝的请求不持有任何预留。

**目录的上限压过 Runner 的索取。** 一个索取超过该模型配置产出量的 Runner，得到的是配置的数额，而预留按那个数额取走。更小的索取会被尊重，因此一个短请求不会占住一个长请求的预算。

## 曾考虑的替代方案

**原样转发 Runner 的请求并附上凭据。** 按上文所述否决：凭据会跟着请求所指之处走，而每一个可能把它指向别处的字段，都变成一件需要记着去剥除的事。

**在 Control Plane 里重建 Provider 请求。** 已否决：那会把 harness 已有的每一个 Adapter——序列化、流式、图片与文件语义——在第二个地方重复一遍，而它必须与第一个保持同步。覆盖那两个决定"哪个模型"和"多少输出"的字段，是让授权真正有意义的最小干预。

**用字段白名单校验请求体。** 已否决：Provider 增加特性的速度快过白名单更新的速度，而一个丢弃未知字段的网关，会弄坏 Adapter 本意要发的请求。对授权与成本要紧的那些字段是已知且很少的；其余是 Adapter 自己的事。

**把授权缓存进 Access Token。** 已否决：Token 的寿命长于一次角色变更，而一个被移出角色的成员会一直调用到它过期为止。按调用询问的代价是一次查表，换来的是即时撤销。

**让 Runner 传自己的最大输出。** 保留，但被封顶。尊重更小的索取是有用的——一个短请求不该占住一个长请求的预算——而更大的索取，正是目录上限存在的理由。

## 后果

这两个包里没有任何东西调用 Provider。`authorize` 产出一份计划，`settle` 关闭它；执行 HTTP 调用、解析凭据引用、统计输入 Token、流式转发响应，属于它前面的那个 Transport。那个 Transport 正是"公司模型调用的内容经过 Control Plane"成为事实的地方，也是设计所要求的缓冲与内容日志限制必须落脚的地方。

`inputTokens` 由调用方提供，因此网关按被告知的数额预留。少报的调用方会少预留。统计属于 Transport，那里请求体已经被解析过了。

`model` 是 OpenAI 兼容请求形态里的字段名，而那是本构建唯一代理的格式。命名不同的 Provider 需要它自己的条目而不是一个猜测，而该常量被导出，因此第二种格式是一次新增而不是一次修改。

目录携带的是输出上限而没有价格，因此账本计的是 Token 而不是钱。按价格加权需要在这里加上费率元数据，而以后补上它会改变一次结算的含义，但不会改变一次结算何时发生。
